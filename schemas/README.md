# schemas/

The record of what has shipped.

## `effects/`

One file per built-in effect: its id, its schema version, and every parameter's key, type,
unit, default and range. Generated by `gen_schemas`, **committed on purpose**, and checked
by `test_schemas` on every build.

These exist because D1's rules cannot be enforced by the code alone. "A parameter key is
immortal" and "bump the schema version on any parameter change" are statements about
yesterday, and the registry only knows about today. Comparing the two is the only moment
anybody can still be told to bump a version and write a migration, and by the time a user's
project fails to load it is far too late.

So: **the files are the authority for what shipped, the registry is the authority for what
the app does now, and the test fails when they disagree.**

They are not generated at build time on purpose. A generated file cannot be reviewed, and
"you changed this parameter's unit" is exactly the kind of line that has to show up in a
diff with somebody's name on it.

### Changing an effect

1. Change it in `EffectRegistry.cpp`.
2. `test_schemas` fails and names the effect.
3. Decide what kind of change it is:
   - **Label, order, slider range, group** are display only. Change freely, no bump.
   - **Widening a hard limit** cannot invalidate a stored value. No bump.
   - **Adding a parameter, tightening a hard limit, changing a default** all change what
     existing content evaluates to. Bump `schema`, add a `legacy_default` where one is
     needed, and write the migration.
   - **Renaming a key, changing a type or a unit** is forbidden. Add a new key, retire the
     old one, migrate.
4. `./build/tests/gen_schemas schemas/effects` and review the diff before committing it.

`validate_against_previous` enforces most of this; the file is what gives it a "previous"
to compare against.

## `preset/`

JSON Schema for the `.rbyset` / `.rbypck` container (D2), plus a worked example.

- `manifest.schema.json` — identity, author, tags, drop target, requires, variants, exposed
  controls, licence and the reserved signature slot.
- `content.schema.json` — the layer-stack fragment. **The same layer shape a `.rbypr`
  project uses**, so there is one layer serialization and one parser rather than two that
  drift apart.
- `example/` — one hand-written preset, a whip pan. `test_schemas` checks it against both
  schemas, checks every effect it names actually exists, and checks it is authored in beats.

Nothing reads presets yet, so these are the format decided rather than the format
implemented. The example is what keeps them honest: a schema with no file written against
it is a guess.

## The general rule

A schema file nobody checks is a comment in a different directory. Everything here is
either enforced by a test or is an example that is itself enforced by a test.
